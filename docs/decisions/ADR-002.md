# ADR-002 — Tauri as privileged browser shell

- **Status:** proposed
- **Date:** 2026-08-13
- **Owners:** repository maintainers
- **Related PRs:** PR-011, PR-012, PR-045
- **Related threats/tests:** shell smoke test, CSP validation, no-remote-URL gate, IPC malformed input

## Contexto

O navegador precisa de uma superfície nativa para abrir janelas, receber input e apresentar a UI privilegiada (omnibox, tabs, sidebar, settings). O core e o engine devem permanecer independentes do shell para que Servo possa ser trocado ou testado isoladamente. Tauri 2 (wry/WebView) fornece lifecycle de janela, frontend local e bridge de comandos sem acoplar o renderer de páginas web ao shell.

PR-011 introduz o bootstrap mínimo: uma janela local redimensionável com frontend HTML estático, CSP restritivo e sem commands, events, invoke bridge genérico ou navegação remota. Esta é a evidência inicial para esta decisão.

## Decisão

Tauri 2 é o shell privilegiado do navegador: lifecycle de janela, frontend local e bridge de comandos tipados e allowlisted. Tauri **não** é o renderer de páginas web — esse papel pertence ao Servo via `engine-host` e `render-surface`. O shell não expõe `invoke` genérico, filesystem, network ou process ao frontend; toda comunicação usa comandos validados pelo core.

### Limites explícitos

- O frontend Tauri conhece apenas o schema de commands/events gerado, não `browser-core`, `servo-engine`, `storage` ou `platform` diretamente.
- `unsafe` é proibido no shell por workspace lint.
- CSP é local-only; `unsafe-inline` limita-se ao stylesheet do frontend estático.
- Nenhuma URL remota é carregada pelo frontend do shell.

## Alternativas consideradas

1. **Electron** — ecossistema maduro, mas empowered Chromium embutido conflita com a decisão de usar Servo como engine e aumenta a surface de ataque.
2. **winit + wgpu direto** — máximo controle, mas exige重建 toda a UI, input handling e platform backend do zero; custo desproporcional para M1.
3. **Sem shell nesta fase** — adia o spike de janela e input; bloqueia PR-012, PR-017 e todas as dependências downstream.

## Consequências

### Positivas

- Lifecycle de janela e frontend local prontos para integrar com `browser-core` em PR-012.
- Frontend isolado do engine e do core, respeitando o boundary de arquitetura.
- CSP e ausência de bridge genérica reduzem a superficie de ataque do shell.

### Negativas e riscos aceitos

- Tauri/wry depende de system libraries (WebKitGTK no Linux, WebView2 no Windows, WKWebView no macOS) que variam por plataforma.
- Atualizações de Tauri 2 podem introduzir breaking changes no config ou na API de commands.

### Mitigações e gates

- Dependências Tauri fixadas em `Cargo.lock`.
- CI instala `libwebkit2gtk-4.1-dev` no Linux.
- Teste de shell valida no-remote-URL, CSP e ausência de invoke bridge.
- Futuras commands terão schema validado e capability-scoped (PR-021, PR-045).

## Evidência

- PR-011: janela Tauri local com frontend estático, CSP restritivo e sem navegação remota — CI green em `a899b9c`.
- `docs/architecture-graph.yaml`: `browser-desktop` em M1 `adds`, dependendo de `browser-core`, `platform` e `tauri`.
- `SECURITY_MODEL.md` e `THREAT_MODEL.md`: frontend é trust zone separada de páginas web.

## Revisão

Esta decisão permanece `proposed` até que:
- PR-012 integre o shell com `browser-core` via commands tipados;
- PR-045 valide o contrato IPC com capability scoping;
- Evidência de abre/fecha em pelo menos Linux e outra plataforma seja registrada.

Qualquer breaking change de Tauri 2 que invalide o lifecycle, CSP ou a bridge de commands reabre esta decisão.
