# ADR-003 — Servo as initial engine via isolated adapter

- **Status:** proposed
- **Date:** 2026-08-13
- **Owners:** repository maintainers
- **Related PRs:** PR-013, PR-016
- **Related threats/tests:** spike build, create/destroy lifecycle, EventLoopWaker/spin_event_loop, WebViewDelegate

## Contexto

O navegador precisa de um engine para renderizar páginas web. A arquitetura aprova Servo como engine inicial por adapter isolado, mas exige uma revisão fixada e um spike que prove a viabilidade do embedding antes de congelar qualquer API.

PR-013 é o spike descartável que examines a API de embedding do Servo na revisão `859bd5edd60c0fb162a1f73c083a23e55474faf7`. O spike não introduz Servo como dependência do workspace nem feature browser — apenas documenta findings e define o contrato conceitual no `engine-api`.

## Decisão

Servo é o engine inicial do navegador, integrado via um adapter isolado (`servo-engine`) que traduz os comandos do `engine-api` para a API de embedding do Servo. A revisão do Servo é fixada e qualquer mudança exige atualização do pin e re-validação.

### Limites explícitos

- APIs instáveis do Servo `main` não viram contrato sem spike e evidência.
- O adapter `servo-engine` é o único crate que conhece tipos Servo.
- `engine-api` permanece engine-neutral; nenhum tipo Servo vaza para `browser-core`.
- Script evaluation, DevTools e permissions estão fora do primeiro contrato.
- O spike é descartável: não se torna API pública estável nem feature browser.

## Alternativas consideradas

1. **Integrar Servo diretamente no workspace** — quebra o boundary de isolamento e acopla o build do browser ao do engine.
2. **Usar WebKitGTK via wry sem Servo** — funciona para o shell, mas não é engine neutro e não permite controle de engine host.
3. **Adiar o spike** — bloqueia PR-016 e todas as dependências downstream de engine.

## Consequências

### Positivas

- Contrato engine-neutral (`engine-api`) pode ser testado com um fake engine sem Servo.
- O adapter isola a complexidade e drift de API do Servo.
- Revisão fixada garante reprodutibilidade.

### Negativas e riscos aceitos

- API de embedding do Servo é instável e sparsamente documentada.
- Atualizações da revisão podem quebrar o adapter.
- System libraries pesadas (WebKitGTK/JSC) são necessárias para compilação nativa.

### Mitigações e gates

- Revisão fixada em `Cargo.lock` e no spike report.
- `engine-api` define o contrato; o adapter implementa.
- CI valida o contrato com fake engine; o adapter real é validado em spike separado.
- PR-016 ratifica o contrato após evidência do spike.

## Evidência

- PR-013: spike report em `docs/spikes/servo-embedding-859bd5e.md` documenta:
  - `ServoBuilder::build()` → `Servo`
  - `WebViewBuilder::new(&servo, rendering_context)` → `WebView`
  - `EventLoopWaker` trait com `wake()` e `clone_box()`
  - `Servo::spin_event_loop()` para processar events
  - `WebViewDelegate::notify_new_frame_ready()` para sinal de repaint
  - `WebView::load()`, `WebView::reload()`, `WebView::go_back()`, `WebView::go_forward()`
  - Limitações: API `Rc<RefCell>` não-`Send`, requer winit ou equivalente para event loop
- Exemplo de referência: `components/servo/examples/winit_minimal.rs`

## Revisão

Esta decisão permanece `proposed` até que:
- PR-016 produza o adapter real com o fake engine passando o contrato;
- Evidência de create/destroy lifecycle em pelo menos Linux seja registrada;
- A revisão do Servo seja revalidada após mudanças upstream quebras.

Qualquer breaking change na API de embedding do Servo que invalide o builder, EventLoopWaker ou WebViewDelegate reabre esta decisão.
